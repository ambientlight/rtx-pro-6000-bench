# SGLang on SM120 with Pearl mining

Engineering plan, 2026-11-23. Serve DeepSeek V4.1 Flash on the four RTX PRO 6000 Blackwell Max-Q GPUs through the existing inference endpoint. **Both prompt prefill and output-token generation must contribute verifiable Pearl work from computations the model actually uses.** Request admission immediately revokes direct F2Pool mining. Completion of the last inference GPU work immediately wakes the four direct miners whenever no other request is pending. Both transitions have zero intentional delay. The independent Windows RTX 5080 is outside this four-GPU scheduling group.

The [SM120 prototype and hardware results](prototype/README.md) cover the first projection, SGLang tensor-parallel execution and direct-miner handoff.

## What to optimize

First establish repeatable mining from both inference phases, including a single active generating stream. Lower mining efficiency during inference is acceptable. Then maximize difficulty-weighted accepted work per wall-clock hour on a fixed traffic mix, subject to serving latency, throughput, model quality and disclosure policy. Attribute work to prefill, decode or standalone idle mining. Report energy, eligible rows, unique attempts and accepted work for each. Issued targets determine how often attempts become shares. Individual requests can complete with zero hits.

The first layer is deliberately small. A full 2,048-token chunk through one block’s attention output projection represents `2048 × 8192 × 5120 = 85,899,345,920` MACs across all four ranks. At the observed four-card idle rate of roughly 1,236 TMAC/s, that is **69.5 microseconds of idle mining**. If the added serving time displaces 1 ms of subsequent full-speed mining, the displaced raw work is about 14 times the work captured from that layer. At continuous 5,000 eligible uncached tokens/s the layer contributes about 0.21 TMAC/s. These are scale estimates. Pool credit, real traffic, and overlap determine the result.

A recorded DeepSeek request with 32,788 uncached input tokens and 6,091 output tokens took 98.92 seconds. At most 16 full prefill chunks would qualify, equivalent to **1.11 ms of dedicated mining from prefill alone** through this projection. At a sustained 2,552 eligible fresh tokens/s, one projection contributes 0.107 TMAC/s (0.0087% of dedicated mining). Covering the same projection in all 40 blocks at unchanged speed would bring that to 4.28 TMAC/s (0.35%). The historical 2,552 rate was a mean of prefill samples. For decode, each full six-row single-stream target verification adds 251,658,240 projection MACs across the four ranks. Estimate decode work from measured real verification rows. Emitted-token count alone cannot reconstruct the number of verification passes. ## Milestones

### 1. Baseline and replay

Record a serving-alone baseline with automatic serving memory clocks, and a standalone-mining baseline at the deployed 280 W cap and 7,001 MHz memory setting. Also record the current simultaneous-services configuration as an operational reference. Capture versions, clocks, temperatures, power, driver, CUDA, cache state, traffic schedule and pool difficulty. Build a repeatable synthetic trace that covers one short request after a long idle period, bursts, overlapping streams, long uncached prompts, prefix hits, cancellations and a return to idle. Include direct SGLang and LiteLLM entry points. Use existing API and streaming checks. [Load accounting](../../scripts/dsv41_load.py#L126) · [Serving checks](../../scripts/dsv41_live_acceptance.py) · [Stream checks](../../scripts/dsv41_stream_delivery_probe.py)

**The baseline is ready** when repeated baseline-versus-baseline runs give a noise estimate for each serving metric, a distribution of first-request-after-idle latency, and a mining reference in difficulty-weighted accepted work per idle GPU-second.

### 2. Demand-driven idle mining

1. At request admission, atomically reserve the four GPUs for serving and revoke outstanding idle grants. Start CPU request preparation immediately while miners drain in parallel. Cover direct and proxied requests, batch dispatch and GPU preprocessing. Transfer the reservation to the scheduler at dispatch without a gap. Release a failed admission before dispatch or a canceled request after its GPU work drains. Keep the reservation across prefill, decode and gaps between streamed tokens.
2. Serialize revocation with each worker's commitment to enqueue its next slice, including GPU job setup and readback. A worker can commit at most one bounded slice at a time. If admission wins the race, the worker parks. If the slice was already committed, it finishes and the worker acknowledges its CUDA completion event. Keep proof submission, clock tuning and pool acknowledgments off this path. Use generation-tagged acknowledgments so that a late message cannot re-enable direct mining. [Miner launch and readback](../../../mining/blackwell_pearl_miner-v1/src/engine.rs#L262) · [GPU job setup](../../../mining/blackwell_pearl_miner-v1/src/engine.rs#L194)
3. As soon as the last admission reservation clears, the scheduler is fully idle and the last inference GPU events complete on all four ranks, push a wakeup to all four warm miners. The last of these events triggers the grant. Resume the saved work position if the pool job is still valid, otherwise use the latest valid job. Keep serving clocks ready for both directions. HTTP response delivery, a utilization poll and the miner's existing 100 ms sleep are outside the control path. An arrival during wakeup revokes the grant under the same launch rule. [Scheduler idle predicate](../../../sglang-dsv41-production-overlay/python/sglang/srt/managers/scheduler.py#L4657) · [Overlap loop](../../../sglang-dsv41-production-overlay/python/sglang/srt/managers/scheduler.py#L1945) · [Current miner pause loop](../../../mining/blackwell_pearl_miner-v1/src/miner.rs#L288)
4. Bound handoff waits. If a controller or worker dies, idle grants expire and the supervisor quiesces the standalone workers. Periodic telemetry is for diagnosis and crash recovery. Exercise late acknowledgments, service restarts, cancellation with a kernel in flight, and multiple requests finishing or arriving together.

Sweep K, queue depth, and work-slice duration against both idle yield and first-request latency. Start with K=65,536/depth 2 as the control and K=16,384/depth 1 as a challenger. At 275 W the prior GPU 0 experiment measured 238 ms versus 60 ms per round with comparable throughput. Two full rounds could therefore take about 477 ms versus 119 ms to drain. Those numbers motivate a test at 280 W and do not measure serving latency. If necessary, shorten the individual launches further. [Prior paired measurements](../../../mining/blackwell_pearl_miner-v1/tuning/README.md#L76)

For interactive traffic, aim for **at most 10 ms of added time to first token at p99** on the first request after mining. Pair the same requests against warm serving alone, including short cache-hit requests that give the drain little time to overlap with tokenization. Record arrival-to-all-GPUs-ready separately. Test automatic serving memory clocks throughout the idle interval and one outstanding mining slice per GPU. Target 2–5 ms per slice by splitting the existing loop over independent output tiles, keeping the nonce, proof dimensions and global tile coordinates intact. Recheck for demand between launches, verify the completed ticket set against an unsliced round, and measure the idle throughput cost. At 275 W on one card, automatic clocks retained 97.7% of the tuned worker's throughput before slicing. Measure both added first-token latency and idle work per second with slicing and serving clocks enabled together on all four GPUs. [Tile loop](../../../mining/blackwell_pearl_miner-v1/kernels/kernel780.cu#L339) · [Clock benchmark](../../../mining/blackwell_pearl_miner-v1/tuning/README.md#L216)

**Measure the return to direct mining as well.** For a warm valid pool job, target **p99 ≤5 ms from final inference GPU completion to the first direct mining kernel running on all four GPUs**, using the latest of their four start times. Use matched clocks for the timestamps. Count clock recovery and job changes separately and also report the overall gap with those cases included. A new arrival that cancels a resume is a distinct outcome. Replay arrivals just before the final inference fence, between the idle grant and the first miner launch, and during the first slice. Include short idle gaps, overlapping streams, slow readers and disconnects. Verify that an old grant can never launch a second slice after revocation. Both the 5 ms resume target and the 10 ms added-first-token target need measurements on this rig.

### 3. Mine one DeepSeek projection during prefill and decode

Develop both paths against offline fixtures in parallel with the handoff. Start with `layers.0.attn.wo_b` in the target model. Pass the execution context at the call site. Preserve the local stream, output dtype and buffer semantics, and run the existing all-reduce exactly once.

| Serving path | First implementation and proof shape per GPU |
|---|---|
| Prefill | An ordinary `EXTEND` batch of 2,048 fresh rows uses the released sampling pattern and opens two activation rows and 64 weight rows. Measure other naturally occurring prefill widths after this reference shape. |
| Single-stream DSPARK decode | The November 23 live server reports block size 5 and target verification width 6. One full target pass already evaluates the anchor and five proposed positions. Mine that same six-row projection during `TARGET_VERIFY` using adjacent activation rows and groups of 16 weight rows. Feed the corrected output to target verification before DSPARK makes its acceptance decision. |
| Batched decode | Use real rows already present in the same forward. Qualify concurrent DSPARK and ordinary non-speculative `DECODE` batches with at least two real rows. For ragged widths, first use complete pairs and handle any tail in the calibrated ordinary path. Track proposed, verified and emitted tokens separately. |
| One token with speculation disabled | Test a two-row encoding of the one quantized activation on the same weight shard. Each row contributes to the emitted token. Compare it with the ordinary calibrated one-row projection at concurrency one. |

The full six-row decode projection per rank is `[6, 2048] × [5120, 2048]ᵀ`. The v3 CPU miner and verifier passed this shape and a two-row shape using a nonsaturating synthetic target. The released vLLM integration has a configurable 1,024-row threshold. The v3 verifier accepts compact 2 × 16 sampled tiles. It requires even sampled dimensions and real indices in bounds, so a direct one-row matrix-vector multiply cannot produce this proof. [CPU shape checks](wo_b_v3.rs) · [vLLM gate](../../../mining/pearl-v1.5.8/miner/vllm-miner/src/vllm_miner/config.yaml#L10) · [Verifier constraints](../../../mining/pearl-v1.5.8/zk-pow/src/api/sanity_checks.rs#L40)

For graph replay, stage job generation, real-row eligibility and an available result slot at stable device addresses before the existing target graph runs. Exclude padding, capture warmups and dummy forwards. Pin the inputs needed for hits before the slot is reused. Keep the configured speculation width, token emission and stream cadence independent of mining. Use the ordinary calibrated path when the current forward has no usable job or proof capacity. [Target forward](../../../sglang-dsv41-production-overlay/python/sglang/srt/speculative/dspark_components/dspark_verify.py#L299) · [Capture mode](../../../sglang-dsv41-production-overlay/python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py#L316) · [Real and padded row counts](../../../sglang-dsv41-production-overlay/python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py#L1378)

For an ordinary single-token step, a CPU fixture splits the calibrated integer activation exactly as `x = 8 × hi + lo`. Both component rows multiply the same weight shard. The fixture extracts v3 tickets from those noised products, removes the noise, and recombines the two corrected outputs. All 5,120 output coordinates matched the direct integer projection. The v3 verifier accepted a hit and rejected a miss at the fixture target. This route doubles the projection's main integer multiply work per useful input row before mining overhead. Apply recombination within each scale group before rescaling. The stock block-FP8 comparison, GPU path and pool submission still need qualification. A two-row proof here reveals enough to reconstruct the full quantized input shard for that token, so use public synthetic traffic for this experiment. [Single-token CPU fixture](singleton_v3.rs)

The prefill multiply is `[2048, 2048] × [5120, 2048]ᵀ` on each rank. The ranks own distinct weight shards. K=2,048 meets v3’s minimum for rank 128. The SGLang CUDA extension should depend directly on the operator and verifier interfaces so it can be built independently of vLLM. Its GPU operator must handle arbitrary signed INT7 inputs, commit both actual operands, derive the dimension-salted seeds, extract the integer transcript, and return the denoised, rescaled result to DeepSeek. The current idle kernel and proof cache specialize in synthetic operands. The released Hopper forward is a reference. A published SM120 implementation that emits both an integer product and a transcript is also a useful independent comparison. [CPU shape probe](wo_b_v3.rs) · [V3 verifier](../../../mining/pearl-v1.5.8/zk-pow/src/api/verify.rs#L101) · [SM120 kernel reference](https://github.com/akoyapool/akoya-miner/blob/0e42b2a50b4cb62cb8995b77420226c2182137ce/native/pearl-gemm/csrc/blackwell/transcript_gemm_sm120.cu#L20-L30)

- **Proof correctness.** Replay identical synthetic-request activations, weights, header, shape, rank and target through CPU and GPU. Compare Merkle roots, salted seeds, exact ticket digest and hit decision for selected tiles across all four ranks. Include finite thresholds yielding both hits and misses, job refresh, difficulty changes, duplicate suppression and stale work. An easy-target proof alone can hide an incorrect GPU digest.
- **Model correctness.** Compare stock block-FP8, calibrated INT7 without mining, and mined INT7 with identical quantization and scales. Check per-shard output before the collective, then assembled logits, task results, DSPARK acceptance and cache-hit/miss consistency. Upstream’s denoising has finite-precision corrections. In the calibrated model variant select precision independently of job availability, proof backpressure and disclosure policy. Use the corresponding ordinary multiply when mining is skipped. Isolate its prefix cache from the serving reference and test alternate chunk boundaries.
- **Serving isolation.** Skip the mining opportunity when the job, eligibility or queue credit is missing. A delayed proof worker must not stall a forward. Bind every candidate to the original header, job generation, pool-session identity, issued share target, tensor shards and quantization version until it is verified or discarded. Verify against the pool target override while preserving the header bytes used in the commitments. Bound scratch, retained tensor references and pinned memory per rank. At the pilot shape the extra INT7 weight copy is 10 MiB and one activation copy is 4 MiB per rank before correction and proof workspace. Measure peak use against live per-rank headroom.
- **Pool and privacy.** Use a synthetic/public traffic profile for the first end-to-end shares. V3 sends a plain proof. At K=2,048 the prefill pattern opens two quantized activation rows (4 KiB) and 64 local weight rows (128 KiB). The compact decode pattern opens two activation rows (4 KiB) and 16 local weight rows (32 KiB). Both also carry authentication data. Current transport uses plain TCP and the idle client retains an accepted proof. Disable payload retention on the inference path and log aggregate counters only. For a private deployment, enable external inference proofs only for eligible traffic and enforce eligibility across the whole batch and cache provenance. Use ordinary inference for mixed or unknown provenance. **The operator is ready for a canary** when one public synthetic request exercises both model paths, consumes their corrected outputs, and a controlled-target replay produces independently verified hits from prefill and from single-stream generation. Include a cached-prefix, long-output run with standalone workers paused throughout generation to isolate decode. For live qualification, demonstrate a uniquely attributable F2Pool acceptance at issued difficulty from each phase over sufficient traffic. Track eligible attempts while waiting for rare shares. Attribute zero inference work to padding, shadow multiplies and standalone mining during a request.

### 4. Hillclimb the whole service

Run four matched configurations.

| Arm | Serving and mining | What the comparison measures |
|---|---|---|
| A | Stock SGLang alone | Reference serving behavior |
| B | A with demand-driven idle mining | Request arrival to miner drain, final inference GPU completion to direct mining on all four GPUs, and idle yield |
| C | B with the ordinary calibrated INT7 pilot projection | Cost and quality impact of replacing the FP8 projection |
| D | C with the fused mined forward enabled | Measure prefill-only, decode-only and both enabled on the same trace to isolate phase costs and their interaction. |

Compare D to A for the user's experience, D to B for net additional mining work, and idle intervals to the dedicated mining baseline.

| Decision | Measurement |
|---|---|
| Does a request slow down? | First-token latency from arrival including queueing and clock recovery, p95/p99 inter-token and streamed output gaps, and output tokens/s. Break out idle-to-first-request, cached-prefix single-stream generation, long prefill and concurrency 1/4/8. |
| Does the model still serve correctly? | Paired output/logit and task-quality checks, streaming, structured responses, speculative acceptance, prefix reuse, cancellation and OOM/recovery under sustained mixed load. Use natural completion for quality evaluation. |
| Does each phase contribute? | Verified unique work and difficulty-weighted accepted work by prefill, decode and idle origin, both per active phase-second and per total wall hour. Record useful model MACs, extra mining arithmetic, actual target-verification rows, unique attempts, stale/rejected work and energy. Use fixed job/target replay for small effects and report actual F2Pool credit separately. |
| Where is the time going? | Handoff and clock transition, quantization, hashing, noising, matrix multiply, correction, all-reduce, proof copies/queue and per-rank memory high-water mark. Use traces for diagnosis and clean runs for promotion. |

Counterbalance run order, repeat under matched cap, thermal and cache conditions, and reserve unseen prompts and jobs for holdout. Also measure the real first request after prolonged idle mining. The target is **zero serving regression**. Predeclare the primary latency, throughput and quality measures before tuning. Report paired deltas with one-sided 95% regression bounds. A literal no-slowdown claim requires those bounds to exclude a slowdown on the primary serving measures. If they only exclude regressions above a particular size, report that size. Use A/A repeatability to size runs and keep profiles with unresolved results in the experiment.

Tune admission and idle launch size alongside the two mined forward paths. Vary operand preparation, weight-tree reuse keyed to shard/config/job, CUDA tile shape, correction fusion and asynchronous hit handling. Compare variants that retain both inference phases and satisfy serving and quality gates. Use the mixed trace to select coverage and to quantify any work displaced during idle intervals.

### 5. Canary, release and FP8

Build a separately versioned candidate image with isolated model/cache state. The November 23 snapshot had only about 1.3 GiB of namespace headroom per serving GPU. Recheck the budget and compare full four-rank images sequentially in a benchmark window on this rig or on matching capacity. Use CPU fixtures and tensor-level replay for earlier iterations. Snapshot the effective deployed stack, preserve the known-good image and miner, and keep independent controls for idle scheduling and inference mining. Validate startup, direct/proxied inference, mining-only operation, pool disconnect, controller restart, stale callbacks and return to reference clocks. Roll back a numerical change together with its cache state. Promote from synthetic canary to any eligible real traffic only after accepting the measured serving, quality and disclosure behavior.

Keep admission, worker control, job snapshots, metrics and queue management reusable across certificate versions. V3 uses integer operands and intermediate checkpoints. V4 has different commitments and proofs and already includes an SM120 FP8 mined forward with decode/no-job fallback on Pearl's development branch. Run separate v4 fixtures and testnet qualification. Select the proof implementation using the job’s supported certificate version. Release v4 pool submission when the network and F2Pool actually issue compatible jobs and a verified share is accepted. Keep the integration disabled by default while measuring the baseline and both four-rank handoffs.
